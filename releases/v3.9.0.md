# LeadCMS SDK v3.9.0 - Clean Content Files and One Checkpoint per Remote

This release moves every server-managed value (`id`, `createdAt`, `updatedAt`, sync tokens) out of your content files and out of loose state files, into one `metadata.json` per remote. It also collects the 3.8.x changes that shipped without notes: live content in development under any bundler, a single `watch` per content directory, and a more tolerant server version check.

Versions covered: 3.8.0, 3.8.1, 3.8.2 and 3.9.0.

## What's New

### `metadata.json` is the remote's checkpoint (format version 2)

Each remote's state now lives in a single file, `.leadcms/remotes/<name>/metadata.json`. Every entity block pairs the sync token the server handed out with the items that token vouches for:

```jsonc
{
  "version": 2,
  "content": {
    "syncToken": "Mq0sICkJ3wg",            // where the next content pull continues
    "items": { "en": { "blog/my-post": { "id": 42, "createdAt": "…", "updatedAt": "…" } } }
  },
  "media":          { "syncToken": "MMWwOCsJ3wg" },   // media has no per-item metadata
  "emailTemplates": { "syncToken": "QFiHICkJ3wg", "items": { "en": { "Welcome": { "id": 5 } } } },
  "sequences":      { "syncToken": "gCTKNywJ3wg", "items": { "en": { "Onboarding": { "id": 1 } } } }
}
```

The separate `<type>-sync-token` files are gone. Keeping the token next to the items it describes means the two can never drift apart, and neither can be committed without the other. Writes are atomic (temp file and rename), so a crash mid-write cannot leave a half-updated checkpoint.

**Commit this file.** The token is the position from which the next pull continues. A clone without it has to pull everything from scratch and, worse, can never learn about items deleted on the remote in the meantime; it also has no `updatedAt` baseline for conflict detection on push. Remotes that are personal to one developer (a local CMS, say) can be ignored selectively with `.leadcms/remotes/local/`.

`leadcms remote show <name>` reads the new layout and prints every recorded token together with the entry counts.

**Programmatic API**: `readSyncToken`, `readSyncTokens`, `writeSyncToken` and `clearSyncToken` replace direct token-file access. `syncTokenPath` remains exported but is deprecated and only used for migration.

### `id`, `createdAt` and `updatedAt` are no longer written to files

Content (MDX and JSON), email templates, sequences and segments are now written without server-managed fields. They are recorded per remote in `metadata.json` instead, and the default remote is treated exactly like any other: a push or pull never rewrites a file just because the server's timestamps moved.

What this changes in practice:

- A push no longer dirties files in git; one working tree can serve several remotes with different ids.
- Comparison ignores these fields on both sides, so files written by older SDK versions still compare cleanly. They are dropped the next time a file is rewritten.
- Rename and deletion cleanup resolve the previous slug from the metadata map. A frontmatter `id` is consulted only as a fallback for files written by older versions.
- Pulling from a non-default remote no longer substitutes the default remote's ids or timestamps into local files.
- Conflict detection on push compares the remote's current `updatedAt` with the value recorded in that remote's `metadata.json`.
- After a remote delete (`push --delete` on content, email templates, sequences or segments) the corresponding metadata entry is pruned, so the map never carries ghosts.

### `leadcms push --yes`

`push` (the joined command) accepts `--yes` / `-y` to skip the confirmation prompt for CI and scripted use. Only the confirmation is skipped: the content-type wizard, when it runs, still asks its questions, and it now validates each answer and asks again instead of silently taking a default. Piping `yes |` into `push` previously answered the wizard as well and created content types with every flag enabled and the wrong format.

### Media deletion by id

`push-media --delete` (and the joined `push --delete`) now removes remote files through the bulk endpoint by id rather than by path. Path-based deletion could not address every file: a file uploaded straight into the media directory was stored under scope `.` and returned 404 for every encoding of its path, leaving it undeletable. Files placed directly in the media directory are now rejected before upload with a pointer to the fix (move them into a sub-folder), since the server requires a folder for every file.

### Live content in development, under any bundler (3.8.0)

Content is read from disk at request time and never imported, so a bundler does not watch it: an edit produces no module change and the open page goes stale. `leadcms watch` now handles this. It watches the content directory, covering edits made by hand and its own writes from the LeadCMS event stream, and records the content's revision in a small generated module. Importing that module from a page gives the dev server a real change to push.

```jsonc
// package.json
{ "scripts": { "dev": "concurrently \"next dev\" \"leadcms watch\"" } }
```

```ts
import { CONTENT_REVISION } from "@/.leadcms/content-revision";
```

The module defaults to `.leadcms/content-revision.js`; set `contentRevisionFile` in `leadcms.config.json` to move it, and add it to `.gitignore`. `leadcms generate-content-revision` writes the same module for production builds. The approach only rewrites a module the site already imports, so it works under Turbopack, Webpack and Vite without a plugin for each. Pass `--local` to skip the remote stream deliberately; without a configured remote the stream is simply not started.

In the same release, the JSON configuration cache became self-invalidating. Entries are validated against the file's mtime and size on every lookup (one `stat`, cheaper than the read and parse it avoids), so editing `header.json` or a form configuration is visible on the next request instead of after a 30-second timer. `clearContentCache()` is exported for long-lived processes that relocate the content directory. `watch` and `generate-content-revision` are local-only and resolve paths through `loadLocalConfig()`, which does not require `url`.

### One watcher per content directory (3.8.1)

A preview container commonly supervises `leadcms watch` as its own process while the dev server starts another. Two recursive watchers on the same tree doubled the filesystem traffic and the log lines. `watch` now takes a lock on the content directory: a second watcher reports which process already covers it and stands down, while still streaming content from the CMS if that is what it was started for. The lock lives in the temp directory keyed by the resolved content path, never appears in the project, is released on exit, and a lock left by a killed process is taken over rather than respected forever.

## Bug Fixes

### Fixed: server version check rejecting versions with build metadata (3.8.2)

`compareVersions` now ignores build metadata and treats missing minor or patch components as zero, so a server reporting `1.5+2262cd79` compares as `1.5.0`. Login previously failed against such instances.

### Fixed: content types created with the wrong flags and format

Piped input reached the content-type wizard (see `push --yes` above). Separately, an API content type whose format is anything other than `JSON` is now mapped to MDX locally; the `MD` format used to be treated as JSON, which made status report every MDX file as modified and produced duplicate `.mdx` files next to JSON components on pull.

### Fixed: stale metadata after remote deletes

Deleting content, an email template, a sequence or a segment on the remote left its entry in `metadata.json`, so a later file with the same slug was pushed as an update to an id that no longer existed.

### Fixed: root-level media files could be uploaded but never deleted

See "Media deletion by id" above.

### Fixed: `watch --local` reporting that no LeadCMS instance was configured

The message now distinguishes an explicit `--local` from a project with no remote at all.

## Upgrade Notes

**`metadata.json` migrates itself.** The first pull or push after upgrading rewrites each remote's `metadata.json` in the v2 layout and deletes the old `<type>-sync-token` files. Commit the result. Older SDK versions read a v2 file as empty and would rewrite it in the old layout on their next run (the new SDK re-migrates it, nothing is lost, but the file churns), so upgrade every checkout and CI job that pulls content to 3.9 together.

**Content files lose their server-managed fields on the next rewrite.** `id`, `createdAt` and `updatedAt` are ignored for comparison, so nothing shows as modified; expect a one-time diff removing those lines the next time a pull or push rewrites a file.

**Media must live in a sub-folder** of the media directory (`public/media/<folder>/...`). A file placed directly in the directory is now refused with a message instead of producing an undeletable remote file.

**`watch-content` is `watch`.** If you adopted 3.8.0 early, the separate `watch-content` command was folded into `leadcms watch` in the same release.

**Scripts** that answered `push` with `yes |` should pass `--yes` instead.
