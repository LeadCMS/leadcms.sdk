# LeadCMS SDK v3.11.0 - Each Site Gets Its Own Redirect Maps

A minor release that closes three ways a multi-site project could ship the wrong site's redirects ([#4](https://github.com/LeadCMS/leadcms.sdk/issues/4)). Single-site projects see no change apart from the stale-map fix and the corrected preview template.

## Why

`generate-redirects-map` read the active site's `redirects.yaml` but wrote its maps to one `redirects/` folder that every site shared. Building one site and then the other rewrote the same `301.map` and `302.map`. A project that kept the folder in git saw it flip on every switch, and the committed copy was wrong for one of the two sites. The preview Docker image made it worse: it copied whatever maps the build context held, so an image built for the second site could serve the first site's redirects.

## New Features

### Redirect maps go to a per-site folder by default

Without an explicit `redirects.outputDir`, a named site now writes its maps to `redirects/<site>/`:

```
redirects/
  acme/301.map
  zenith/301.map
  zenith/302.map
```

The output directory is resolved in this order:

1. `--output <dir>`
2. `redirects.outputDir`, top-level or per site, used as written
3. `redirects/<site>/` for a named site
4. `redirects/` in a single-site project (unchanged)

The folder is build output, regenerated from `redirects.yaml` on every build, so it belongs in `.gitignore`.

### `SiteContext.redirectsOutputDir`

`getActiveSite()`, `resolveSite()` and `listSites()` now report the absolute folder a site's maps go to, so a postbuild or Docker step can copy the right one without knowing the site's name:

```js
import { getActiveSite } from "@leadcms/sdk";
fs.cpSync(getActiveSite().redirectsOutputDir, "out/redirects", { recursive: true });
```

`leadcms site show` prints it as `Redirect maps:`. Running `leadcms site add` on a single-site project without an `outputDir` now says in its summary that the maps move from `redirects/` to `redirects/<name>/`.

## Bug Fixes

### Fixed: a site's `redirects` replaced the top-level block instead of refining it

A site's keys were spread over the top level shallowly, so a site that set only `redirects.outputDir` silently lost the inherited `pathPattern` and `trailingSlash`:

```json
{
  "redirects": { "pathPattern": "/{slug}/", "trailingSlash": "both" },
  "sites": {
    "second": { "root": "sites/second/.leadcms", "redirects": { "outputDir": "redirects/second" } }
  }
}
```

```
before: second → {"outputDir":"redirects/second"}
after:  second → {"pathPattern":"/{slug}/","trailingSlash":"both","outputDir":"redirects/second"}
```

The second site's maps had been generated with the default `/{language}/{slug}` pattern and no trailing-slash variants. A site's `redirects` is now merged with the top-level one key by key.

`languageDomains` deliberately keeps replace semantics. It lists a site's languages: merging would give one brand another brand's domains, and it would make a site that maps one language look multi-language, which changes how redirects are stored. A site that sets `languageDomains` gets exactly the map it sets. A site's `redirects` or `languageDomains` that is not an object is now rejected with a configuration error.

### Fixed: stale maps survived when a site had no redirects

When `redirects.yaml` was missing or empty, `generate-redirects-map` returned early and left any `301.map` / `302.map` in the output folder untouched. In a shared folder those were another site's maps; in a per-site folder they were this site's redirects from before the last one was deleted. Either way nginx kept serving them. Stale maps are now removed (except with `--dry-run`).

### Fixed: the preview Docker template installed maps it did not generate

`templates/docker/preview/Dockerfile` copied `/app/redirects/*.map` into `/etc/nginx` straight after `COPY . .`, picking up committed or leftover maps, possibly another site's. It now generates the maps for its own `LEADCMS_SITE` during the build, in its own `RUN` so a failure fails the build:

```dockerfile
RUN npx leadcms generate-redirects-map --output /etc/nginx && \
    touch /etc/nginx/301.map /etc/nginx/302.map
```

### Fixed: the preview container never pulled content at startup

The template's startup script ran `npx leadcms fetch`, which is not a command. The CLI printed its help and exited 0, so the `|| echo "Warning: …"` fallback never fired and the container started on whatever content was in the image. It now runs `npx leadcms pull` and then regenerates the redirect maps. Both happen before supervisord starts nginx, so the redirects pulled at startup are live without a reload.

- 1520 tests passing across 78 suites

## Upgrade Notes

**Multi-site projects without `redirects.outputDir`:** maps move from `redirects/` to `redirects/<site>/`. Anything that copies `redirects/*.map` (a postbuild step, a Dockerfile) must copy from the site's folder instead; `getActiveSite().redirectsOutputDir` gives the path. Delete the old `redirects/301.map` and `redirects/302.map` and add `redirects/` to `.gitignore`.

**Multi-site projects with a top-level `redirects.outputDir`:** nothing moves. That folder is still shared by every site and holds whichever site was generated last. To get per-site folders, remove the top-level `outputDir`, or set `redirects.outputDir` inside each site (the inherited `pathPattern` and `trailingSlash` are now kept).

**Projects using the preview Docker template:** `leadcms docker` overwrites `Dockerfile`, `nginx.conf` and `preview/` in place, so diff against a fresh copy or apply the two changes by hand: replace the `cp /app/redirects/…` step with the `generate-redirects-map --output /etc/nginx` step above, and change `leadcms fetch` to `leadcms pull` in the startup script. Note that the container now really pulls at startup when `LEADCMS_URL` and `LEADCMS_API_KEY` are set.
