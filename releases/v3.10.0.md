# LeadCMS SDK v3.10.0 - Named Sites: One Codebase, Several Content Trees

A minor release adding **multi-site support**. A single site codebase can now serve several sites, each with its own content, media, default language, remotes and sync state, selected per command or per build with `--site` / `LEADCMS_SITE`. Without a `sites` block in the config nothing changes.

## Why

Named remotes (v3.5) isolate the *identity* of the same content across instances: production, develop, local. They deliberately share one content directory. A second brand, a regional edition or a white-label deployment is the opposite case: different content, same code. Configuring a brand as a remote made `status` report hundreds of phantom changes and let a `push` upload one brand's pages into the other brand's instance. The only real answer was a second repository, and two repositories drift apart within months.

## New Features

### Named sites in `leadcms.config.json`

```json
{
  "defaultLanguage": "en",
  "sites": {
    "acme": {
      "root": ".leadcms",
      "mediaDir": "public/media",
      "remotes": { "prod": { "url": "https://cms.acme.example.com" } },
      "defaultRemote": "prod"
    },
    "zenith": {
      "root": "sites/zenith/.leadcms",
      "mediaDir": "sites/zenith/public/media",
      "defaultLanguage": "en-GB",
      "remotes": { "prod": { "url": "https://cms.zenith.example.com" } },
      "defaultRemote": "prod"
    }
  },
  "defaultSite": "acme"
}
```

A site's `root` expands to its seven entity directories and to its remote state base `{root}/remotes`, so `acme/prod` and `zenith/prod` keep separate checkpoints. Any directory key set on the site overrides that one directory; `mediaDir` inherits the top-level value and must be unique per site. Other top-level keys are shared defaults. `url`, `remotes` and `defaultRemote` are rejected at the top level once `sites` exists, because silently ignoring them would show up only as an empty pull.

Sites and remotes are orthogonal. `leadcms pull --site zenith --remote dev` pulls the `zenith` site's content from `zenith`'s develop instance into `zenith`'s tree, using `zenith`'s `dev` checkpoint. Nothing about `acme` is read or written.

### `--site` / `-s` on every command

Every pull, push, status and watch command, `generate-redirects-map`, `generate-content-revision`, `add-content`, `login` and the `remote` subcommands take `--site <name>`. Resolution order is the flag, then `LEADCMS_SITE`, then `defaultSite`. Commands print the site next to the remote:

```
🏷  Site: zenith            (sites/zenith/.leadcms)
🌐 Remote: prod (default) → https://cms.zenith.example.com
```

In single-site mode the site line is omitted, and `--site` or a stale `LEADCMS_SITE` is an error, with the same wording remotes use.

### `leadcms site` commands

```bash
leadcms site list [--names]
leadcms site add zenith --language en-GB --remote prod=https://cms.zenith.example.com
leadcms site show zenith
leadcms site set-default zenith
leadcms site remove zenith          # config entry only; files stay in place
```

On a project without a `sites` block, the first `site add` wraps the current configuration into a named site after confirmation. The existing root stays `.leadcms`, so every file and every checkpoint under `.leadcms/remotes/` is picked up unchanged: no re-pull. A flat `url` becomes a remote named `default`, which keeps its state directory and its `LEADCMS_API_KEY` fallback.

`remote add | remove | set-default | show | reset` accept `--site` and act on that site's `remotes` block.

### Site-qualified API keys

Two sites may both call their production instance `prod`. Keys are resolved as `LEADCMS_SITE_{SITE}_REMOTE_{REMOTE}_API_KEY`, then `LEADCMS_REMOTE_{REMOTE}_API_KEY`, then `LEADCMS_API_KEY`. A CI job builds one site and normally needs only the last two. `leadcms login --site zenith` writes the site-qualified variable.

### Build-time API

No signature changes. `getAllContentRoutes()`, `getCMSContentBySlugForLocale()`, `getAvailableLanguages()` and the rest read the effective configuration, which is now per site, so `LEADCMS_SITE=zenith pnpm build` renders `zenith`'s tree and languages without touching page code. Two additions:

```ts
import { getActiveSite, listSites, configure } from "@leadcms/sdk";

getActiveSite(); // { name, isDefault, root, defaultLanguage, contentDir, mediaDir, stateBaseDir, remotes, … }
listSites();     // every configured site; a single "default" entry in single-site mode
configure({ site: "zenith" }); // programmatic selection, above LEADCMS_SITE
```

Content references media as `/media/...`, so `public/media` must point at the active site's media directory at build time. The README documents a prebuild link step; the preview Docker template passes `LEADCMS_SITE` through as a build argument.

## Internal Changes

- `src/lib/site-context.ts` holds the resolution rules: `resolveSite()`, `listSites()`, `getActiveSite()`, root expansion, validation and the state base for a site.
- `buildConfig()` resolves the active site first and merges `DEFAULT_CONFIG ← top-level keys ← root expansion ← per-site keys ← environment ← configure()`. The raw config file is still cached for a minute; site resolution happens on every call, so switching `LEADCMS_SITE` within one process takes effect immediately.
- `resolveRemote()` derives `stateDir` from the site's `{root}/remotes`; the hard-coded `.leadcms/remotes` constant is gone. Single-site paths are byte for byte what they were.
- `leadcms-helpers.ts` exports its directory and language bindings as `let`; `configureForSite()` rebinds them when a bin script is invoked directly with `--site`. Through the `leadcms` CLI the flag is exported as `LEADCMS_SITE` before the command starts.
- Build-time reads (`getLeadCMSConfig()` in `cms.ts`), `generate-redirects-map` and the import-time bindings in `leadcms-helpers.ts` now resolve the configuration with `loadLocalConfig()` instead of `loadConfig()`. Directories, languages and the active site never depended on a reachable remote; demanding a `url` there made a site whose instance was not configured yet fall back to the default paths. The remote is still validated wherever it is actually used.

## Upgrade Notes

**Nothing to do for single-site projects.** No `sites` block means the implicit `default` site with today's paths.

**`-s` now means `--site` everywhere.** `push`, `status`, `push-media` and `status-media` used to accept `-s` as an undocumented alias for `--scope <scopeUid>`. That alias is removed; `--scope` keeps its long form. A script passing `-s blog` fails with a site error rather than filtering media, so the change is loud.

**Adding a second site to an existing project:**

1. `leadcms site add zenith --language en-GB --remote prod=https://cms.zenith.example.com` and confirm the migration; name the existing site when asked (or pass `--existing-name`).
2. `leadcms pull -s zenith` performs a full first sync into `sites/zenith/.leadcms/` and creates its `remotes/prod/metadata.json`. Commit it, like the existing checkpoints.
3. Add the media link step and one CI job per site with `LEADCMS_SITE` set. See "Multiple sites in a build" in the README.

**`.env` files with `LEADCMS_SITE`** in a project that has no `sites` block now fail every command. That is deliberate: a stale variable naming a site that does not exist should stop a build, not select nothing.
